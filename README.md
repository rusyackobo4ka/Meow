# Meow — подборщик комплектов мебели

Ассистент для хакатона СФЕДУ, который подбирает комплект мебели по диалогу с покупателем и каталогу объявлений.

Цель проекта — собрать комплект из трёх предметов: стола, стула и лампы. Все товары должны соответствовать условиям покупателя, находиться в одном городе и укладываться в заданный бюджет. Предусмотрен самовывоз.

## Как работает проект

Покупатель описывает свои пожелания обычным языком. Ассистент анализирует переписку, определяет требования и подбирает подходящие товары из каталога.

В проекте используется LLM `google/gemma-4-31B-it` через API организаторов.

**Важный принцип:** языковая модель отвечает только за извлечение условий из диалога. Сам подбор комплектов выполняется детерминированным Python-кодом по структурированным данным каталога. Это делает результат воспроизводимым и независимым от субъективных решений модели.

## Возможные статусы ответа

Каждый запрос возвращает ровно один из трёх статусов.

### `clarify` — требуется уточнение

Возвращается, если не хватает основных условий или они неоднозначны:

- город;
- бюджет;
- список необходимых категорий.

Ассистент задаёт уточняющий вопрос.

### `ok` — комплект найден

Возвращается, если все основные условия известны и в каталоге есть полный подходящий комплект.

Ассистент возвращает от одного до трёх вариантов комплектов.

### `no_match` — подходящий комплект не найден

Возвращается, если условия известны, но в текущем каталоге нет полного комплекта, соответствующего требованиям.

Ассистент объясняет, что мешает подбору и какие условия можно изменить.

## Архитектура проекта

Обработка каждого запроса проходит через несколько последовательных этапов.

### 1. Extract — извлечение условий

LLM анализирует историю переписки и преобразует её в структурированные данные `Conditions`.

Определяются:

- город покупателя;
- бюджет;
- необходимые категории товаров;
- неподдерживаемые категории;
- ограничения по характеристикам товаров.

### 2. Dialog — проверка условий

Система проверяет, достаточно ли информации для подбора.

Если отсутствует город, бюджет или список категорий, возвращается `clarify`.

### 3. Catalog — фильтрация каталога

Загружаются объявления и отбираются товары, которые соответствуют городу покупателя и заданным ограничениям.

### 4. Selector — подбор комплектов

Python-алгоритм формирует комбинации товаров:

- один стол;
- один стул;
- одна лампа.

Проверяется общая стоимость комплекта и соответствие бюджету.

### 5. Dialog — формирование результата

Если подходящие комплекты найдены, возвращается `ok`.

Если подходящих комбинаций нет, возвращается `no_match` с объяснением причины.

## Быстрый запуск

Для работы проекта требуется Python 3.10 или новее.

Внешние Python-пакеты для запуска не нужны. Используется стандартная библиотека Python, включая `urllib`.

### 1. Настройка переменных окружения

Доступ к модели организаторы предоставляют индивидуально. API-ключ нельзя добавлять в репозиторий.

Перед запуском необходимо выполнить:

```bash
export LLM_BASE_URL=https://sfedu-hackathon-ai-gateway.sfedu-hackathon-ai-gateway.workers.dev/v1
export LLM_MODEL=google/gemma-4-31B-it
export LLM_API_KEY=ваш-индивидуальный-ключ
export LLM_USER_AGENT=hackathon-team-01/1.0
```

### 2. Запуск обработки запроса

```bash
./run --catalog /абсолютный/путь/catalog.json < request.json > response.json
```

Также доступны альтернативные способы запуска:

```bash
python3 main.py --catalog /путь/catalog.json
```

```bash
python3 -m meow --catalog /путь/catalog.json
```

## Формат входных данных и ответа

На вход программа получает один JSON-объект:

```json
{
  "messages": [
    {
      "role": "user",
      "content": "Мне нужен стол, стул и лампа в Ростове. Бюджет — 15000 рублей."
    }
  ]
}
```

Поддерживаются роли `user` и `assistant`.

Сообщения должны чередоваться. Первое и последнее сообщение обязательно должны принадлежать пользователю.

На выходе программа возвращает ровно один JSON-объект.

Основные требования к CLI:

- вход читается до EOF;
- в stdout выводится только JSON-ответ;
- завершающий перевод строки разрешён;
- логи и диагностические сообщения отправляются в stderr;
- при успешной обработке возвращается код 0;
- при ошибке запуска, конфигурации или внешнего сервиса возвращается ненулевой код.

Техническая ошибка не должна подменяться статусом `no_match`.

На обработку одного запроса отводится до 120 секунд, включая обращения к модели.

## Переменные окружения

Все параметры передаются через переменные окружения. Значения по умолчанию не предусмотрены.

Если переменная отсутствует или содержит некорректное значение, возникает `ConfigError`. Сообщение об ошибке выводится в stderr, программа завершается с кодом 1.

| Переменная | Назначение |
| --- | --- |
| `LLM_BASE_URL` | Базовый URL API моделей организаторов |
| `LLM_MODEL` | Имя используемой модели |
| `LLM_API_KEY` | Индивидуальный API-ключ команды |
| `LLM_USER_AGENT` | Идентификатор клиента команды |

Ожидаемая модель: `google/gemma-4-31B-it`.

Пример настроек находится в `.env.example`.

Файл `.env` уже добавлен в `.gitignore`. Автоматической загрузки `.env` нет, поэтому переменные необходимо экспортировать самостоятельно.

В финальной проверке организаторы установят необходимые переменные окружения.

## Подключение к языковой модели

HTTP-клиент находится в файле `meow/llm_client.py`.

Для выполнения запросов используется стандартная библиотека `urllib`, без дополнительных зависимостей.

Модель вызывается через:

```http
POST {LLM_BASE_URL}/chat/completions
```

Используются следующие HTTP-заголовки:

- `Authorization: Bearer ...`;
- `Content-Type: application/json`;
- `User-Agent`.

### Формат извлечения данных

Для извлечения условий используется `response_format` с форматом `json_schema` и параметром `strict: true`.

Схема находится в `EXTRACT_SCHEMA` внутри `meow/extract.py`.

Если API возвращает ошибку схемы HTTP 400 или модель выдаёт некорректный JSON, клиент повторяет запрос с форматом `json_object` и дополнительно проверяет обязательные ключи.

### Параметры генерации

- `temperature = 0`;
- `max_tokens = 600`.

Это позволяет сделать извлечение условий более стабильным.

### Ограничения и обработка ошибок

В клиент встроена обработка ограничений API:

- суммарный размер текстов сообщений — не более 32 768 байт;
- размер всего тела запроса — не более 65 536 байт;
- проверка ограничений выполняется до отправки запроса;
- общий дедлайн составляет примерно 100 секунд, чтобы оставить запас до ограничения CLI в 120 секунд;
- повторные запросы выполняются только для HTTP 429 и 503;
- учитывается заголовок `Retry-After` и оставшееся время выполнения.

Сетевые сбои, некорректные ответы модели и превышение дедлайна приводят к `LLMError`.

Ошибка отправляется в stderr, программа завершается с кодом 1.

### Назначение основных файлов

**Точка входа:**

- `run` — запуск программы через Python;
- `main.py` — точка входа для `./run` и `python3 main.py`;
- `chat.py` — интерактивный диалог в терминале.

**Основной пакет `meow`:**

- `main.py` — сборка приложения и зависимостей;
- `assistant.py` — управление последовательностью обработки запроса;
- `models.py` — основные типы данных: `Conditions`, `Constraint`, `Listing`, `Kit`, `Question`;
- `config.py` — чтение и проверка переменных окружения;
- `llm_client.py` — HTTP-клиент для работы с языковой моделью;
- `extract.py` — извлечение условий из истории диалога;
- `catalog.py` — загрузка и фильтрация каталога;
- `selector.py` — подбор комплектов в рамках бюджета;
- `dialog.py` — формирование ответов `clarify`, `ok` и `no_match`;
- `__main__.py` — запуск через `python3 -m meow`;
- `__init__.py` — инициализация пакета.

Папка `demo/` содержит тестовый каталог, входные запросы и ожидаемые результаты.

Папка `tests/` содержит end-to-end тесты и проверки контракта.

Архитектурный принцип: граф объектов собирается только в `meow.main.build_assistant`. Доменные классы не читают переменные окружения и не создают собственные зависимости самостоятельно.

## Интерактивный режим

Для демонстрации работы ассистента предусмотрен интерактивный терминальный режим.

Запуск:

```bash
python3 chat.py /путь/к/catalog.json
```

Пользователь может вести полноценный диалог с ассистентом.

При каждой новой реплике `chat.py` запускает `./run` с накопленной историей сообщений и выводит ответ в удобном формате.

Это позволяет демонстрировать продолжение диалога, уточнение условий и подбор мебели.

## Демонстрационные сценарии

Для запуска всех демонстрационных сценариев используется команда:

```bash
bash demo/run_demo.sh
```

Скрипт запускает все запросы из `demo/requests/`, использует `demo/catalog.json` и сравнивает полученные ответы с эталонными результатами из `demo/expected/`.

Между вызовами предусмотрены паузы по 3,5 секунды для соблюдения ограничений API.

В проекте предусмотрено семь сценариев:

1. `01` — подбор комплекта с ограничениями по характеристикам;
2. `02` — продолжение уже начатого диалога;
3. `03` — запрос с неподдерживаемой категорией;
4. `04` — отсутствие подходящего комплекта в Ростове;
5. `05` — защита от prompt injection в описании объявления;
6. `06` — защита от prompt injection в сообщении покупателя;
7. `07` — уточнение города и бюджета.

## Тестирование

Для запуска тестов используется `pytest`.

### 1. Офлайн-проверка эталонного решателя

```bash
python3 -m pytest tests/test_e2e.py -k reference
```

Проверяет соответствие ожидаемых статусов содержимому каталога без обращения к языковой модели.

### 2. Полный набор end-to-end тестов

```bash
python3 -m pytest tests/test_e2e.py
```

Для выполнения необходим действующий `LLM_API_KEY`.

### 3. Проверка CLI

```bash
python3 -m pytest tests/test_e2e.py -k cli_
```

Проверяет контракт запуска и корректность взаимодействия с командной строкой.

### Что проверяют живые тесты

- набор ключей в JSON-ответе;
- корректность возвращаемого статуса;
- уникальность ID товаров;
- наличие всех необходимых категорий;
- соответствие города;
- соблюдение ограничений характеристик;
- точное значение `total_rub`;
- отсутствие текстов объявлений в объяснениях.

Живые тесты помечены `@live` и пропускаются, если `LLM_API_KEY` не задан.

Между запросами соблюдается пауза с учётом лимита примерно 20 вызовов за 60 секунд.

Полный живой прогон занимает около 8–10 минут.

## Защита от манипуляций (Prompt Injection)

Безопасность обработки данных — один из важных принципов проекта.

Описание товаров рассматривается исключительно как данные, а не как инструкции для языковой модели.

В system prompt явно запрещено выполнять команды, содержащиеся в описаниях объявлений.

Дополнительно реализованы следующие меры:

- объяснения строятся только на основе структурированных полей каталога;
- текст объявлений не используется как источник инструкций;
- инъекции в пользовательских сообщениях не должны менять системные правила;
- инъекции в сообщениях ассистента не должны менять системные правила;
- атрибуты товаров обрабатываются как недоверенные данные.

Защита проверяется специальными тестовыми сценариями:

- `inj_catalog_*` — инъекции в описаниях объявлений;
- `inj_user_*` — инъекции в сообщениях покупателя;
- `inj_assistant_*` — инъекции в сообщениях ассистента.

## Отладка и типовые ошибки

### Ошибка Cloudflare 1010

Если HTTP-ответ не является JSON и содержит сообщение `error code: 1010`, вероятно, шлюз не принял стандартный User-Agent Python.

Решение — указать собственный `LLM_USER_AGENT`.

### HTTP 429 — превышен лимит запросов

Клиент автоматически учитывает `Retry-After` и повторяет запрос, если позволяет оставшееся время.

### HTTP 401 или 403 — проблема авторизации

Необходимо проверить правильность API-ключа и срок доступа, предоставленного организаторами.

### Ошибки модели и сетевые сбои

Невалидный ответ модели, проблемы сети или превышение дедлайна приводят к `LLMError`.

Все служебные сообщения, включая RAW/COND извлечённые условия и диагностические ошибки, выводятся исключительно в stderr.

## Итог

Meow объединяет возможности языковой модели и детерминированных алгоритмов.

LLM понимает покупателя, Python подбирает товары, а пользователь получает готовый комплект мебели с учётом города, бюджета и характеристик.

Результат основан на проверяемых комбинациях товаров из каталога.
